# 📘 **Clase 1 – Introducción a Sistemas de Información II**
## 🔹 Temas principales de Clase 1

### 1. **Organización y Empresa**

- **Organización**: grupo de individuos que trabajan coordinadamente para un fin común.
    
    - Tipos: Con fines de lucro, sin fines de lucro, estatales.
        
- **Empresa**: organización que produce bienes o servicios para obtener un beneficio económico.
    
    - Funciones: productiva, social, valor añadido, toma de riesgos.
        

### 2. **Recursos Empresariales**

- **Dato**: símbolo sin contexto ni interpretación (ej. “23°C”).
    
- **Información**: datos + contexto + utilidad (ej. “Temperatura actual en Buenos Aires: 23°C”).
    
- **Conocimiento**: uso de la información para tomar decisiones (ej. “Si mañana la temperatura es alta, aumentar stock de bebidas frías”).
    

👉 Diferencia clave:

- **Dato → Información → Conocimiento** = niveles crecientes de valor.
    

### 3. **Sistemas y Sistemas de Información**

- **Sistema**: conjunto de elementos interrelacionados que trabajan para un objetivo.
    
- **Sistema de Información (SI)**: sistema que recopila, procesa, almacena y distribuye información para apoyar la toma de decisiones en una organización.
    
    - Ejemplos: ERP, CRM, sistemas de inventario.

# 📘 **Clase 2 – Ingeniería de Software y Requisitos**

## 🔹 Temas principales de Clase 2

### 1. **Proceso y Procedimiento**

- **Proceso**: conjunto de actividades relacionadas que transforman **entradas** en **salidas**.
    
    - Entradas: materia prima, datos, eventos.
        
    - Transformación: actividades + recursos (humanos, tecnológicos, financieros).
        
    - Salidas: productos, servicios, facturas, órdenes.
        
- **Procedimiento**: pasos detallados para ejecutar una actividad específica dentro de un proceso.
    
    - Ejemplo: pasos para cortar, lijar y ensamblar piezas de una silla.
        

### 2. **Ingeniería de Software**

- Surge en 1968 (Fritz Bauer, conferencia OTAN).
    
- **Definición**: aplicación de un enfoque **sistemático, disciplinado y cuantificable** al desarrollo, operación y mantenimiento de software.
    
- Busca software: **económico, confiable y eficiente**.
    

#### Capas de la IS

1. **Enfoque de calidad** (base).
    
2. **Proceso** (organiza las etapas).
    
3. **Métodos** (técnicas de análisis, diseño, pruebas).
    
4. **Herramientas** (soporte automático o semiautomático).
    

### 3. **Ciclo de Vida del Software (SDLC)**

- También llamado **Proceso de Desarrollo de Software**.
    
- Incluye todas las fases desde la definición de requisitos hasta el retiro del sistema.
    

#### Fases principales:

1. **Planificación y análisis**: qué problema resolver, qué debe hacer el software.
    
2. **Diseño**: cómo se implementará la solución.
    
3. **Construcción**: programación y pruebas unitarias.
    
4. **Pruebas e integración**: validar que cumple requisitos.
    
5. **Implantación y mantenimiento**: puesta en marcha, mejoras y corrección de errores.
    

👉 En esta clase se enfatiza en la **fase de planificación y análisis de requisitos**.

### 4. **Ingeniería de Requisitos**

- Disciplina dentro de la IS que estudia **cómo descubrir, documentar y gestionar requisitos**.
    
- Implica recolección, análisis, especificación, validación y gestión de cambios.
    

### 5. **Roles en proyectos de software**

- **Usuario final**: aporta necesidades reales.
    
- **Cliente/patrocinador**: financia y define objetivos de negocio.
    
- **Ingeniero de requisitos**: elicita, analiza y documenta necesidades.
    
- **Desarrolladores**: construyen el sistema.
    
- **Testers**: verifican que se cumplan los requisitos.
    

### 6. **Dominio del problema**

- Conjunto de elementos, procesos, reglas y actores relacionados al **entorno donde se aplicará el sistema**.
    
- Ejemplo: en una heladería → sabores, stock, pedidos, clientes, producción.

# 📘 **Clase 3 – Requisitos de Software**

## 🔹 Temas principales de Clase 3

### 1. **¿Requisito es lo mismo que requerimiento?**

- En **ingeniería de software** (técnicamente):
    
    - **Requisito** = condición o capacidad que debe cumplir el sistema.
        
    - **Requerimiento** = proceso de obtención/definición de requisitos.
        
- En la práctica muchas veces se usan como sinónimos.
    

---

### 2. **Características de un buen requisito**

1. **Correcto** → representa lo que realmente necesita el cliente.
    
2. **Completo** → no falta información relevante.
    
3. **No ambiguo** → solo puede interpretarse de una manera.
    
4. **Consistente** → no contradice otros requisitos.
    
5. **Verificable** → puede comprobarse mediante pruebas o revisiones.
    
6. **Realista/Factible** → implementable con recursos y tecnología disponibles.
    
7. **Necesario** → contribuye a los objetivos del sistema.
    
8. **Trazable** → puede rastrearse desde su origen hasta su implementación.
    

👉 Ejemplo de mal requisito: _“El sistema debe ser rápido”_ ❌.  
👉 Ejemplo refinado: _“El sistema debe procesar 100 transacciones por segundo”_ ✅.

---

### 3. **Objetivo, límite y alcance**

- **Alcance del producto** → se mide contra **requisitos**.
    
    - Responde: ¿el sistema cumple con lo que se necesita?
        
- **Alcance del proyecto** → se mide contra la **planificación**.
    
    - Responde: ¿se hicieron todas las tareas necesarias para entregar el producto?
        

Ejemplo:

- Producto: sistema de pedidos e inventario.
    
- Proyecto: fases de análisis, desarrollo, pruebas, migración y capacitación.
    

---

### 4. **Clasificación de requisitos**

1. **De negocio**
    
    - Expresan el valor o beneficio esperado.
        
    - Ejemplo: _“Mejorar la experiencia del cliente reduciendo reclamos por errores en pedidos”_.
        
2. **Funcionales**
    
    - Qué debe hacer el sistema.
        
    - Ejemplo: _“El usuario podrá registrarse con un email único”_.

	- Subtipos:

		- **Servicios/funciones principales** → ej: _“Registrar ventas”_.
		    
		- **Reglas de negocio** → ej: _“Un cliente no puede reservar más de 12 clases al mes”_.
		    
		- **Excepciones y validaciones** → ej: _“Si no hay stock, mostrar mensaje de error”_.
        
3. **No funcionales**
    
    - Cómo debe comportarse el sistema (calidad, restricciones).
        
    - Ejemplo: _“El sistema debe procesar pagos en menos de 2 segundos”_.

	- Subtipos:
    
	    - **Rendimiento** → tiempo de respuesta, capacidad (_“procesar 100 pedidos/minuto”_).
	        
	    - **Usabilidad** → facilidad de uso (_“interfaz accesible desde móviles”_).
	        
	    - **Fiabilidad** → disponibilidad, tolerancia a fallos (_“uptime del 99,9%”_).
	        
	    - **Seguridad** → autenticación, cifrado (_“doble factor de autenticación”_).
	        
	    - **Mantenibilidad** → facilidad de actualización (_“código documentado en Java”_).
	        
	    - **Portabilidad** → entornos donde puede ejecutarse (_“compatible con Windows y Linux”_).
        
4. **De dominio**
    
    - Reglas específicas del negocio o industria.
        
    - Ejemplo: _“Los medicamentos deben incluir fecha de caducidad”_.
        
5. **De transición**
    
    - Necesarios para pasar del sistema actual al nuevo.
        
    - Ejemplo: _“Migrar datos históricos de clientes desde el sistema anterior”_.
        
6. **De restricciones de diseño/implementación**
    
    - Limitaciones técnicas o de recursos.
        
    - Ejemplo: _“El sistema debe desarrollarse en Java y usarse con PostgreSQL”_.
        

👉 También se ven clasificaciones según: **nivel de abstracción** y **prioridad (Volere template)**.

---

### 5. **Gestión de requisitos**

- Actividades: Capturar, Documentar, Priorizar, Validar, Controlar cambios, Mantener trazabilidad.
    
- Beneficios: reduce riesgos, asegura alineación con objetivos del negocio, evita errores costosos.

# 📘 **Clase 4 – Elicitación de Requisitos**

## 🔹 Temas principales de Clase 4

### 1. **Definición de Elicitación**

- Primer paso en la **ingeniería de requisitos**.
    
- No es solo “recopilar” lo que pide el cliente, sino **descubrir necesidades reales**, interpretarlas y validarlas.
    
- Técnicas: entrevistas, talleres, encuestas, observación.

---

### 3. **Empatía en la elicitación**

- **Empatía** = ponerse en el lugar del usuario y comprender su contexto.
    
- Permite: tomar mejores decisiones, evitar malentendidos, generar valor real.
    

4 puntos clave para empatizar:

1. **Contexto**: dónde y cómo operará el sistema (cultura, hardware, regulaciones).
    
2. **Dominio de la información**: entender el lenguaje del usuario (ej. “cliente” puede significar distintas cosas).
    
3. **Interacciones y actividades**: cómo trabajan usuarios y procesos actualmente.
    
4. **Comportamiento esperado**: cómo debe reaccionar el sistema en distintas situaciones.
    

---

### 4. **Proceso de Elicitación**

Entradas → Actividades → Salidas

**Entradas**: visión del producto, stakeholders, artefactos existentes, procesos actuales.  
**Actividades**:

1. **Planificación y preparación**
    
    - Definir objetivos, alcance preliminar, identificar stakeholders.
        
    - Seleccionar técnicas (entrevistas, workshops, observación).
        
    - Preparar guías de preguntas.
        
2. **Ejecución (aplicar técnicas)**
    
    - Hacer entrevistas, observar, preguntar, guiar reuniones.
        
    - Manejar conflictos.
        
    - Mantener empatía.
        
3. **Resultados (salidas)**
    
    - Modelos iniciales (casos de uso, historias de usuario, diagramas de contexto).
        
    - Reglas de negocio identificadas.
        
    - Lista priorizada de necesidades.
        
    - Matriz de stakeholders.
        
    - Riesgos y supuestos.
        

---

### 5. **Desafíos comunes en la elicitación**

- Stakeholders no saben lo que quieren.
    
- Expresan necesidades en lenguaje poco claro.
    
- Pueden tener necesidades contradictorias.
    
- Diferencias entre lenguaje técnico y de negocio.
    

👉 Solución: entrevistas bien estructuradas, observación, repreguntar y validar.

# 📘 **Clase 5 – Análisis de Requisitos, Casos de Uso y DFD**

## 🔹 Temas principales de Clase 5

### 1. **Ciclo de Vida de los Requisitos** (repaso y enfoque en análisis)

1. Elicitación.
    
2. **Análisis de requisitos**.
    
3. Especificación.
    
4. Validación y verificación.
    
5. Gestión de cambios y trazabilidad.
    

---

### 2. **Análisis de requisitos**

- Fase donde se **refinan y detallan** los requisitos obtenidos en la elicitación.
    
- Objetivo: lograr requisitos **claros, verificables, completos, factibles y necesarios**.
    

#### Actividades principales:

1. **Clasificación de requisitos** → funcionales, no funcionales, de dominio, restricciones.
    
2. **Depuración y refinamiento** → reescribir requisitos vagos o ambiguos.
    
    - Ejemplo: _“El sistema debe ser seguro”_ ❌ → _“El sistema debe exigir autenticación de dos factores a administradores”_ ✅.
        
3. **Detección y resolución de conflictos** entre stakeholders.
    
4. **Modelado y estructuración** → uso de diagramas (casos de uso, historias de usuario, BPMN, DFD, ERD).
    
5. **Priorización** de requisitos según importancia y criticidad.
    

---

### 3. **Casos de Uso UML**

- Técnica para modelar **funcionalidades del sistema desde el punto de vista del usuario**.
    
- Elementos:
    
    - **Actores** (usuarios u otros sistemas que interactúan).
        
    - **Casos de uso** (funcionalidades, expresadas con verbos).
        
    - **Relaciones** (incluye, extiende, asociaciones).
        

👉 Ejemplo:

- Actor: _Cliente_.
    
- Caso de uso: _Reservar turno_.
    
- Relación: _Reservar turno_ incluye _Validar pago_.
    

#### Especificación de casos de uso

- Documento que detalla cada caso de uso.
    
- Secciones típicas:
    
    - ID y nombre.
        
    - Actor.
        
    - Descripción.
        
    - Precondiciones.
        
    - Postcondiciones.
        
    - Flujo normal.
        
    - Flujos alternativos.
        
    - Excepciones.
        
    - Requisitos funcionales/no funcionales relacionados.
        

---

### 4. **Diagramas de Flujo de Datos (DFD) y de Contexto**

- **DFD**: representación gráfica del **flujo de información** en un sistema.
    
    - **Procesos** → transformaciones (círculos/burbujas).
        
    - **Flujos de datos** → información en movimiento (flechas).
        
    - **Almacenamientos** → depósitos lógicos de datos (líneas dobles).
        
    - **Entidades externas** → actores fuera del sistema (cuadrados).
        
- Enfoque **Top-Down**: de lo general (nivel 0, diagrama de contexto) a lo detallado (niveles 1, 2…).
    

👉 **Diagrama de Contexto**:

- Nivel más alto (visión global).
    
- Representa el sistema como un solo proceso y sus interacciones con entidades externas.
